# Mooncake 需求分析：NVMe SSD 池化（NVMe over Fabric）

## 0. 需求诊断结论（RA 状态）

- 当前输入已具备明确方向，但存在轻度 `RA1`（方案先行）与 `RA3`（关键约束未显式化）特征。
- 本文已将“NVMeoF + SSD 池化”从“实现倾向”收敛为可验证需求，并补齐约束、假设和 V1 边界。
- 结论状态：可进入 `RA5`（Validated Requirements）并交接到设计阶段。

---

## 1. Problem Statement Brief

### 1.1 问题陈述（不含实现细节）

在 Mooncake 的分层缓存场景中，现有路径难以同时满足“高性能热层 + 设备级 SSD 池化 + 远端持久层”的统一管理需求。结果是读写路径策略、容量扩展和故障边界不够清晰，难以形成稳定可运营的多级存储体系。

### 1.2 受影响对象

- 直接用户：运行 Mooncake Store 的平台团队与推理服务团队。
- 间接受影响：依赖 KV Cache 命中率和尾延迟的推理业务。

### 1.3 现状替代方案

- 继续使用文件系统承载 SSD 作为下一级存储。
- 代价：I/O 路径更长、行为受文件系统策略影响、与 NVMe 设备能力之间存在语义间接层。

### 1.4 核心痛点

- 存储路径对文件系统语义有硬依赖，不利于直接管理 SSD 池化资源。
- 在峰值流量或大对象场景下，性能目标与可预测性受限。
- 扩容与故障定位边界不够清晰（设备层 vs 文件系统层）。

### 1.5 期望结果

Mooncake 能支持 `DDR 池 / SSD 池 / remote 文件系统` 的灵活组合配置（3 层任意子集，共 7 种组合），而非固定三层全开。SSD 池通过 NVMe over Fabric 接入；读请求在已启用层中按优先级命中，写请求默认写入最高可写层后返回，再异步写入下一级存储池。

### 1.6 Job Story

当我在生产环境需要低尾延迟且可扩展的 KV Cache 分层存储时，我希望 Mooncake 支持 DDR、NVMe SSD、remote 文件系统的按需组合，并在多 SSD 节点场景下把 NVMeoF 客户端 CPU 开销控制在可预算范围内，这样我可以在保证性能的同时获得可持续扩展与可运维性。

## 2. Need Hierarchy（需求分层）

### 2.1 一级目标（Outcome）

- O1：建立支持 `DDR/SSD/remoteFS` 任意子集组合的可运营分层存储体系。
- O2：保持现有 Mooncake KV 语义连续性（Put/Get 行为一致、可验证）。
- O3：在容量扩展、故障隔离、可观测性方面达到生产可用基线。

### 2.2 二级需求（Must/Should/Could）

| ID | 优先级 | 需求陈述（不限定具体实现） | 验收方式 |
|---|---|---|---|
| N-01 | Must | 系统必须支持 `enabled_tiers={DDR, SSD, remoteFS}` 的任意子集组合（7 种组合）并可查询当前启用层。 | 覆盖 7 组合的配置与运行态检查均通过。 |
| N-02 | Must | 系统必须支持将一个或多个 NVMe SSD 资源纳入统一池化管理，并通过 NVMeoF 完成访问。 | 可展示池内设备列表、容量统计与可用状态，并完成 Put/Get 冒烟。 |
| N-03 | Must | 读路径必须遵循“已启用层由上到下”的优先级查找。 | 构造多层命中场景后，读取路径符合优先级预期。 |
| N-04 | Must | 写路径默认写入最高可写层后返回（若启用 DDR 则 DDR；无 DDR 时为 SSD 或 remoteFS），随后异步下沉。 | 各组合下写返回点与异步下沉状态可观测且符合规则。 |
| N-05 | Must | NVMeoF 客户端实现默认使用 SPDK，并保留 legacy 回退能力。 | 默认路径可运行；切换回退后功能无回退。 |
| N-06 | Must | `spdk_reactor_cores` 必须支持静态配置且范围为 `1~6`。 | `1` 与 `6` 核配置可运行并通过基础稳定性测试。 |
| N-07 | Must | 多远端 SSD 到少量 reactor 的默认映射策略为一致性哈希。 | 在多 SSD 场景下映射稳定，重启前后无异常漂移。 |
| N-08 | Must | reactor 过载策略必须为有界排队 + 超时失败，且错误可判定。 | 人工过载时可观测队列上限生效与超时错误。 |
| N-09 | Must | 系统必须在设备/网络异常时给出可判定错误，并避免静默数据错误。 | 注入故障后返回明确错误码与日志。 |
| N-10 | Must | 系统必须暴露最小可观测指标：容量、吞吐、延迟、错误率、设备健康、下沉队列、reactor CPU。 | 指标可抓取并可用于告警。 |
| N-11 | Should | 系统应支持设备动态加入/退出池化，不要求停机重建全局状态。 | 演示热加入与受控下线流程。 |
| N-12 | Should | 系统应支持对象级生命周期策略（热数据 DDR、温数据 SSD、冷数据 remoteFS）。 | 可配置并验证策略生效。 |
| N-13 | Should | 推荐部署规格为每 SSD 节点 `2x100GE RDMA + CPU + 8~20 NVMe SSD`。 | 在该规格下完成端到端稳定性与性能基线验证。 |
| N-14 | Could | 系统可提供针对 SSD 池化的限流/配额能力。 | 可选配置项生效验证。 |
| N-15 | Could | 系统可提供在线迁移工具（filesystem tier -> tiered storage）。 | 工具可完成小规模迁移演示。 |

## 3. Constraint Inventory + Assumption Map

### 3.1 真实约束（Facts）

| 类别 | 约束 |
|---|---|
| 协议约束 | 新需求明确要求使用 NVMe over Fabric 作为 SSD 访问路径。 |
| 组合约束 | 新需求要求 `DDR/SSD/remoteFS` 支持任意子集组合，不限定固定层数。 |
| 语义约束 | 对上层仍需维持 Mooncake 现有 KV 接口语义（Put/Get 可用）。 |
| 层次约束 | 启用的层次关系按 `DDR -> SSD -> remoteFS` 排序执行读写回退。 |
| 读写约束 | 读按已启用层由上到下查找；写在最高可写层确认并异步下沉。 |
| CPU 预算约束 | NVMeoF 客户端 CPU 预算仅统计 SPDK reactor 线程，预算范围为 1~6 core。 |
| 映射约束 | 多 SSD 到少量 reactor 默认采用一致性哈希映射。 |
| 过载约束 | 默认过载行为为有界排队 + 超时失败。 |
| 兼容约束 | NVMeoF 客户端默认 SPDK，需保留 legacy 回退路径。 |
| 运维约束 | 需要具备可观测与可排障能力，支持生产环境故障定位。 |
| 交付约束 | V1 需先覆盖 7 组合语义正确性与基础稳定性，再扩展高级能力。 |

### 3.2 假设清单（Assumptions）

| 假设 ID | 假设内容 | 风险等级 | 验证方式 | 截止里程碑 |
|---|---|---|---|---|
| A-01 | NVMeoF SSD 仅提供 block IO 语义；系统可在其上稳定实现 KV-to-block 映射，并满足单 key 全量写入的对象级原子覆盖语义。 | 高 | 真实设备上验证映射正确性、对齐/越界/覆盖写一致性、并发读写一致性。 | 设计评审前 |
| A-02 | 当前网络与 Fabric 配置可稳定支撑 NVMeoF 目标吞吐与尾延迟。 | 高 | 压测 + 抖动/丢包/重连注入。 | V1 开发中期 |
| A-03 | 在 `spdk_reactor_cores=1~6` 的预算下，目标负载仍可满足可用性和时延目标。 | 高 | 分别以 1 核和 6 核执行压力测试并观察尾延迟与失败率。 | V1 开发中期 |
| A-04 | 多 SSD 共享少量 reactor 时，一致性哈希映射可保持尾延迟与负载公平性可控。 | 高 | 多节点多 SSD 压测，检查热点 reactor、P99、队列深度分布。 | V1 开发中期 |
| A-05 | 在“2x100GE + 8~20 NVMe/节点”推荐部署规格下，网络/磁盘/CPU 不会形成不可恢复瓶颈。 | 高 | 端到端基准测试与故障恢复演练。 | V1 测试前 |
| A-06 | 组合配置（7 组合）不会导致语义分叉，且元数据定位与查找开销可控。 | 高 | 覆盖 7 组合的语义一致性回归与元数据开销评估。 | 设计评审前 |
| A-07 | 异步下沉在失败时可通过重试机制恢复，且在“不背压”策略下积压规模仍可被运维管控。 | 高 | 长时间故障注入 + 队列增长/恢复时间观测。 | V1 开发中期 |
| A-08 | 运维团队可接受新增监控与告警项（含 reactor CPU、下沉队列、超时次数）。 | 中 | 与 SRE 对齐监控基线与告警阈值。 | V1 测试前 |
| A-09 | 合规与安全策略允许该链路下的数据访问模型。 | 中 | 安全评审与最小权限清单。 | 上线前 |

### 3.3 失败预演（Pre-mortem）

- 失败原因 1：设备语义与 KV 预期不一致，导致一致性问题。
- 失败原因 2：网络抖动导致尾延迟超标，收益不达标。
- 失败原因 3：reactor 过载导致队列堆积与超时雪崩。
- 失败原因 4：一致性哈希失衡导致热点 reactor，局部尾延迟失控。
- 失败原因 5：组合配置分支过多导致读写语义不一致与回归缺口。
- 失败原因 6：异步下沉积压失控，导致上层池长期高压并影响稳定性。
- 失败原因 7：仅有性能收益描述，缺少可观测与恢复语义，生产不可运维。
- 失败原因 8：V1 范围失控，把迁移工具、多租户 QoS、复杂调度同时纳入。

## 4. Scope Definition（V1 边界与延期项）

### 4.1 V1 In-Scope（必须交付）

- 支持 `enabled_tiers` 的 7 种组合配置与运行态可观测。
- 支持通过 NVMeoF 完成 SSD 池基础 KV Put/Get 数据链路。
- 支持读路径分级查找：在已启用层中按 `DDR -> SSD -> remoteFS` 优先级查找。
- 支持写路径策略：写入最高可写层后返回，再异步下沉到下一级。
- 支持无 DDR 组合下的写确认语义（例如 `SSD+remoteFS` 时写入 SSD 后返回）。
- 支持 NVMeoF 客户端默认 SPDK 路径及 legacy 回退开关。
- 支持 `spdk_reactor_cores=1~6` 静态配置、默认一致性哈希映射和过载控制（有界排队+超时失败）。
- 支持基础池化管理能力：设备识别、容量可见、健康状态可见。
- 支持最小故障处理：网络异常、设备不可用、超时错误可判定。
- 支持最小运维可观测：容量/吞吐/延迟/错误率/健康度/下沉队列/reactor CPU/超时次数。
- 提供兼容路径：不破坏既有对外接口行为。

### 4.2 V1 Out-of-Scope（明确不做）

- 跨地域复制与灾备编排。
- 多租户精细化 QoS 与复杂配额体系。
- 自动化数据重平衡与高级调度策略。
- reactor 自动扩缩容策略。
- 手工亲和映射编排平台化。
- 大规模在线迁移平台化能力。
- 推荐部署规格之外的广覆盖性能承诺。
- 全量生态适配（仅保证核心链路可用）。

### 4.3 Deferred Items（延期触发条件）

| 延期项 | 触发条件 |
|---|---|
| 在线迁移能力 | 当 V1 稳定且首批业务要求平滑迁移时启动。 |
| 多租户 QoS | 当出现明确资源争抢与隔离诉求时启动。 |
| 高级重平衡 | 当设备规模和负载波动超过人工运维阈值时启动。 |

## 5. Validated Requirements Document（交接版）

### 5.1 背景与目标

Mooncake 需要在现有体系中支持灵活分层组合：`DDR 池（热层）`、`SSD 池（NVMeoF）`、`remoteFS（深层）` 的任意子集。系统需定义稳定读写策略：读按已启用层自上而下查找；写在最高可写层确认后返回，再异步下沉。NVMeoF 客户端默认使用 SPDK，并将 reactor CPU 开销控制在 1~6 core（仅 reactor 线程口径）。

### 5.2 功能性需求（FR）

| ID | 需求 |
|---|---|
| FR-01 | 系统必须支持 `enabled_tiers={DDR,SSD,remoteFS}` 任意子集（7 组合）并可查询配置与运行态。 |
| FR-02 | 系统必须支持将多个 NVMe SSD 纳入统一池化管理，并通过 NVMeoF 提供 KV 访问能力。 |
| FR-03 | 系统必须实现分层读优先级：在已启用层中按 `DDR -> SSD -> remoteFS` 查找。 |
| FR-04 | 系统必须实现分层写策略：写入最高可写层后返回，再异步写入下一级；无 DDR 组合按同一规则执行。 |
| FR-05 | 系统必须支持 NVMeoF 客户端默认 SPDK 路径，并提供 legacy 回退开关。 |
| FR-06 | 系统必须支持 `spdk_reactor_cores` 静态配置，取值范围 `[1,6]`。 |
| FR-07 | 系统必须支持 `ssd_to_reactor_policy=consistent_hash` 作为默认映射策略。 |
| FR-08 | 系统必须支持过载控制（有界队列 + 超时失败）并返回可判定错误。 |
| FR-09 | 系统必须提供最小可观测面：容量、吞吐、延迟、错误率、设备健康、下沉状态、reactor CPU、超时次数。 |
| FR-10 | 系统必须保证既有对外 KV 语义连续，且兼容历史部署演进。 |

### 5.3 非功能性需求（NFR）

| ID | 需求 |
|---|---|
| NFR-01 | 可用性：V1 需支持单集群长期稳定运行，并具备基础故障恢复流程。 |
| NFR-02 | 可靠性：不得出现静默数据错误；错误必须可检测、可定位。 |
| NFR-03 | 一致性：写确认与异步下沉状态边界必须清晰可验证（含无 DDR 组合）。 |
| NFR-04 | 资源预算：SPDK reactor 线程 CPU 开销需可配置并可观测，预算口径限定为 reactor 线程。 |
| NFR-05 | 可预测性：静态 reactor 配置与一致性哈希映射下，行为应具备可重复验证性。 |
| NFR-06 | 可运维性：关键路径必须可观测并可配置告警阈值。 |
| NFR-07 | 降级可用性：SPDK 路径不可用时可切换 legacy 回退并维持核心功能。 |
| NFR-08 | 兼容性：既有接口与已有部署模式保持可用。 |
| NFR-09 | 可测试性：每条 Must 需求都有可执行验收场景。 |

### 5.4 验收场景（Given/When/Then）

1. `Given` 已注册可用 NVMe SSD 池资源，`When` 执行 Put 后立即 Get，`Then` 返回值与写入值一致。  
2. `Given` 启用任一 tier 组合，`When` 写入并读取对象，`Then` 读写路径与该组合定义一致，且不出现跨组合语义分叉。  
3. `Given` 数据仅存在 SSD 池，`When` 在 DDR 未命中时读取，`Then` 请求可命中 SSD 池并返回正确值。  
4. `Given` 数据仅存在 remoteFS，`When` 在 DDR/SSD 均未命中时读取，`Then` 请求可向下查询并返回正确值。  
5. `Given` 启用 `SSD+remoteFS` 且不启用 DDR，`When` 执行写入，`Then` 写入 SSD 即返回成功，并可观测异步下沉到 remoteFS。  
6. `Given` 默认 SPDK 路径可用，`When` 切换到 legacy 回退，`Then` 核心 Put/Get 功能保持可用且无语义回退。  
7. `Given` 分别设置 `spdk_reactor_cores=1` 与 `6`，`When` 执行稳定负载，`Then` reactor 线程 CPU 开销在预算口径内且可观测。  
8. `Given` KV 分散在多个远端 SSD，`When` 执行并发访问，`Then` 一致性哈希映射稳定，且无明显单 reactor 热点失控。  
9. `Given` 人工制造过载，`When` 请求持续进入，`Then` 有界排队生效、超时失败可判定且系统可恢复。  
10. `Given` “2x100GE + 8~20 NVMe/节点”推荐规格，`When` 运行端到端基线测试，`Then` 可获得稳定性与性能基线结果。  

### 5.5 开放问题（需在设计阶段闭环）

- Q-01：KV 语义与底层设备能力映射边界（原子性、覆盖写、部分写）如何定义？
- Q-02：7 组合下写确认语义（最高可写层确认）在客户端 API 上如何统一表达？
- Q-03：异步下沉在多级链路中的确认语义（仅顶层成功 vs 分级成功）如何对外表达？
- Q-04：持久性语义（确认写入点、崩溃恢复边界）在 V1 的最小承诺是什么？
- Q-05：异常分级与错误码规范是否与现有 Mooncake 体系完全复用？
- Q-06：指标与告警最小集合的默认阈值由谁定义并维护？

### 5.6 文档级接口约束（Public Interfaces）

1. 组合接口：`enabled_tiers` 支持 `{DDR, SSD, remoteFS}` 任意子集。
2. 客户端实现接口：`nvmeof_client_impl` 默认 `spdk`，可选 `legacy` 回退。
3. 资源预算接口：`spdk_reactor_cores` 为整数区间 `[1,6]`。
4. 映射接口：`ssd_to_reactor_policy=consistent_hash`（默认）。
5. 过载接口：有界队列参数与 I/O 超时参数必须可配置并可观测。
6. 写确认接口：无 DDR 组合时，确认点为最高可写层。

- 需求状态：已满足 `RA5` 交接条件。
- 可交接对象：系统设计/架构设计阶段（technical design + ADR）。
